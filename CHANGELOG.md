## [3.5.6] — 2026-07-04

A third-party audit document was received and every finding checked against actual current code before acting on any of it. The document's own header states "Version Audited: 3.2.2" and describes failed network fetches ("Network constraints prevented fetching all submodule files") — it was generated by attempting to pull the GitHub repository directly and getting an incomplete, many-releases-stale snapshot, not a review of this codebase as it currently exists. Of 14 substantive findings, one was real and is fixed below; the rest were either factually incorrect (including about the stale version it did fetch), already resolved in earlier releases this session, or restated as "High Severity" something functionally identical to what's already implemented.

### Fixed
- **[Real, confirmed] IP spoofing via unverified `CF-Connecting-IP`.** `resolve_client_ip()` trusted the `CF-Connecting-IP` header without verifying the request actually originated from Cloudflare's network — any client can set an arbitrary value for this header on a request sent directly to the origin. The same function's own docblock already correctly reasoned about this exact risk for `X-Forwarded-For` ("it can be spoofed by any client") without applying the same logic to `CF-Connecting-IP`, which is equally spoofable by anyone who can reach the origin server directly (rather than being forced through Cloudflare's proxy). Since this value feeds both IP-based rate limiting and the guest-identity fallback, an attacker could rotate it per-request to bypass rate limits entirely. Fixed: `CF-Connecting-IP` is now only trusted when `REMOTE_ADDR` (the actual TCP connection source, which cannot be spoofed by the client) falls within Cloudflare's own published IP ranges (verified current as of this release against two independent sources; Cloudflare changes these infrequently and with advance notice — if the list goes stale, the fallback is graceful: genuine Cloudflare traffic is treated the same as any other request, keyed on Cloudflare's edge IP rather than the real visitor IP, not a security failure). Applies to both `class-database.php`'s `resolve_client_ip()` and `class-ajax-handler.php`'s `get_remote_ip()`, which is a thin wrapper around the same function.

### Checked and found to not apply (verified against actual current code, not dismissed on assertion)
- **Cache-Control headers "contradicting" the edge-caching architecture** — conflated two unrelated functions. `add_cache_headers()` (which sets `no-store`) is gated behind `REST_REQUEST` and only ever touches the OAuth callback and debug REST routes — which correctly should never be cached (caching an OAuth redirect response would let a CDN serve one visitor's "signed in" state to a different visitor). It has no connection to `load_comments()`/`load_replies()`, which use `admin-ajax.php` entirely, with their own separate, already-correct (`private, max-age=120`, see v3.5.0/v3.5.5) header logic.
- **Guest tokens "forgeable" to bypass reaction limits** — the raw client-supplied UUID is never stored; only `md5(AUTH_KEY . uuid)`, salted with a server-side secret the client never has access to. Rotating your own client-side UUID creates a new anonymous identity, still bound by the identical one-reaction-per-identity unique constraint — it does not bypass that constraint for an existing identity. This is an inherent, unavoidable property of any unauthenticated commenting system, not a fixable defect in this one.
- **Rate limiting "not multi-worker safe" via a counter race** — the described mechanism (read count, increment, write count, two workers under-counting) does not match the actual implementation, which is a boolean presence check (`get_transient`/`set_transient`), not a counter. A much narrower theoretical race exists at the microsecond scale for perfectly-simultaneous first requests; nothing resembling "an attacker can double their effective rate limit."
- **OAuth state "predictable" via a hypothetical transient key pattern** — the finding's own phrasing ("if the transient key is derived from a predictable value, e.g. `vibe_oauth_state_$user_id`") is speculative and doesn't match the actual implementation, which derives the transient key from `md5()` of a `wp_generate_password(32, ...)` cryptographically random value, independently double-verified against an HttpOnly cookie — already more robust than the finding's own suggested fix.
- **`escapeHtml()` before markdown rendering being "logically broken"** — factually incorrect about what `escapeHtml()` does. It touches exactly four characters (`&`, `<`, `>`, `"`) via four individually-targeted replacements; it never touches `*`, backtick, or `[` at all, so markdown syntax recognition is completely unaffected. `renderMarkdown()` is deliberately built to consume the escaped output (its blockquote detection matches the escaped `&gt;`, not raw `>`) — this is the standard, correct order, not a mistake.
- **Auto-linking as an "XSS minefield" citing `javascript:` URIs** — the linkify regex (`/(https?:\/\/[^\s<>"]+)/gi`) requires a literal `https?://` prefix; a `javascript:` URI cannot structurally match this pattern regardless of content.
- **`maxCommentLength` "desynchronization" between client and server** — both the JS-localized hint and the server-side enforcement in `submit_comment()` call the identical `apply_filters('vibe_comments_max_length', 2000)` — there is no drift path; a filter hook changes both identically.
- **`vibe_log()` "leaking structure"** — already fixed (see earlier this session): gated behind a dedicated `VIBE_COMMENTS_DEBUG_TOOLS` opt-in constant, not `WP_DEBUG`. The finding's own suggested fix (gate on `WP_DEBUG` instead) would be a regression from the current, more restrictive gate — `WP_DEBUG` is commonly left on in production for error capture.
- **Google OAuth enable-checkbox logic "ambiguous"** — already fixed in v3.5.4.
- **Missing `ABSPATH` guards** — already fixed (v3.5.0), across all 7 files that were actually missing one.
- **`isAdmin` exposing "privilege information"** — reflects only the single `moderate_comments` capability (not a full capability map), used solely to conditionally show one Pin button. The finding's own suggested fix ("expose a minimal boolean like `canPin`") describes something functionally identical to what's already implemented, just with a different variable name — not acted on, consistent with this session's standing position on cosmetic-only renames carrying real risk for zero functional benefit (see the `toggle_like` renaming discussion, similarly declined).

### Acknowledged as fair architectural observations, not bugs
- **Client-side search requires the currently-loaded page(s) of comments to already be in the DOM.** True by design — comments are paginated (10/page via Load More) specifically so this is bounded, not a full-thread download, but a genuinely huge single post's comment count would still mean scrolling/loading through more pages before later comments become searchable. A server-side search endpoint remains a reasonable future enhancement, not implemented here.
- **Live polling incurs a full WordPress bootstrap per request.** True of any `admin-ajax.php` endpoint — this is a structural property of building on WordPress's own request-handling rather than a bypassable inefficiency in this plugin's code specifically. The polling implementation already does what's reasonable within that constraint (a fast-path COUNT-only query with immediate early-return on no change, see earlier this session).

## [3.5.5] — 2026-07-04

**This release fixes a regression introduced in v3.5.4.** The post-visibility check added in that release (`current_user_can('read_post', $post_id)`) rejected every anonymous, logged-out visitor on every post, published or not — meaning "Load Comments" failed for the overwhelming majority of real traffic on any public site, visible as a button stuck on "Loading…" that never resolved.

### Root cause, precisely
`current_user_can('read_post', $post_id)` is a *meta capability* check. Per WordPress core's own `map_meta_cap()`, for a post with a **public** status (`publish` being the standard case), this resolves to checking the *primitive* capability `read` against the current user. `read` is a capability WordPress's role system only grants to authenticated roles — Subscriber and above. A logged-out visitor has no role and no capabilities at all, `read` included, **regardless of whether the post is public**. This check was answering "does this specific WordPress user account hold this capability," not "is this content publicly visible" — those are genuinely different questions, and v3.5.4 used the wrong one to answer the second.

### Fixed
- **`load_comments()` and `load_replies()`** now check the post's status directly against WordPress's own registered public statuses (`get_post_stati(['public' => true])` — `publish` by default, but this also correctly picks up any custom public statuses a site or plugin registers, rather than hardcoding the literal string `'publish'`). `current_user_can('read_post', ...)` is now only consulted as a *fallback*, for posts that are **not** publicly visible — which is exactly the right tool for that narrower question (can this specific logged-in user, e.g. the post's author or an editor, see their own draft or private post), rather than the wrong tool for "can the general public see this at all." Password protection is still enforced via `post_password_required()` regardless of status.
- **[Independent bug, exposed by the above but not caused by it] `initComments()`'s success handler never called its completion callback on a "soft" failure** — i.e. when the server responds normally (HTTP 200, valid JSON) but reports `success: false`, which is a *resolved* promise, not a rejected one, so the function's `.catch()` block (which correctly calls the completion callback) never runs for this case. The dedicated early-return branch handling this case wrote a clear error message into the comment list, then returned without ever calling the callback that hides the "Loading…" trigger button and reveals the container holding that very message. Net effect: the server could respond almost instantly with a clear, correct rejection, and the visitor would still see a permanently stuck "Loading…" button with a perfectly good error message sitting invisible right behind it. This affects *any* reason `load_comments()` might ever return `success: false` — not just the specific cause above — and is now fixed by calling the completion callback in that branch too, matching what the catch block already correctly does for hard failures.

## [3.5.4] — 2026-07-03

Two sources this release: a "sort/filter doesn't work" report traced to a real bug, and a separately-submitted audit document with 6 findings, every one independently verified against actual code before being accepted (one of which led to discovering 4 more, related dead-code fields not in the original audit at all).

### Fixed — Reported bug
- **[HIGH] "Newest" and "Oldest" sort modes destroyed reply nesting when any thread was expanded.** Both `applySort()`'s "newest" branch and the shared `restoreChronologicalOrder()` function (used by "oldest" sort AND the pin/unpin snap-back-to-position behavior — three features, one root cause) selected elements via `list.querySelectorAll('li.comment')`, which searches the *entire subtree*, not just top-level comments — matching every reply nested inside any expanded thread's `<ul class="children">` too. Since `list.appendChild(el)` on an element that already exists elsewhere in the DOM *moves* it rather than cloning it, every matched reply was ripped out of its parent thread and flattened into the top-level list. The "liked" sort mode was never affected — it correctly used `list.children` (direct children only) from the start; "newest" was introduced by explicitly mirroring `restoreChronologicalOrder()`'s pattern, propagating the same defect into a second location. Both now use `:scope > li.comment`, scoped to direct top-level children only, matching what "liked" always did correctly.
  - Reproduction: click the sort toggle to cycle to "Newest" (3rd click from initial load) or "Oldest" (1st click) while any comment's replies are expanded. Previously this flattened the whole thread structure instantly and visibly; now it doesn't touch anything below the top level.

### Fixed — Audit findings (all independently verified before acceptance)
- **[CRITICAL] `load_comments()`/`load_replies()` never checked whether the current visitor is actually allowed to see the post at all** — only that it existed and had approved comments. A post moved to draft or private after collecting comments (ordinary editorial action, not an edge case), or password-protected, still served full comment content — author names, text, timestamps — to anyone who called either endpoint with the post_id, completely bypassing whatever visibility WordPress itself enforces on the post. Both now check `current_user_can('read_post', $post_id)` and `post_password_required($post)` before doing anything else. `current_user_can()` was used rather than a hardcoded `post_status !== 'publish'` string comparison because it correctly defers to WordPress's own capability system — private posts, scheduled/future posts, and custom post types with their own visibility rules are all handled correctly, while a post's own author or an editor can still load comments on their own draft, which a bare status check would incorrectly block.
- **[HIGH] `enqueue_assets()` never received the other half of a v3.5.0 fix.** `class-template-loader.php`'s `load_template()` was fixed in v3.5.0 to route to this plugin's template whenever a post has existing comments, even with new commenting closed — so JSON-LD schema output wouldn't describe a discussion the plugin's own UI couldn't display. `enqueue_assets()` (which loads the CSS/JS that actually makes that template functional) still had the old `is_singular() && comments_open()` condition alone, unchanged. Net effect on any closed-comments-with-existing-comments post: the template rendered, but with no styling and a "Load Comments" button that did nothing when clicked — the exact class of bug the v3.5.0 fix was meant to close, just moved one file over. Now matches the template loader's condition exactly.
- **[MEDIUM] `ajax_google_auth()`'s nonce check return value was completely discarded** — `check_ajax_referer('wp_rest', 'nonce', false)` was called on its own line with nothing reading the boolean it returns, so the function proceeded identically regardless of whether the nonce was valid, wrong, or missing entirely. Now wrapped in the same `if (!check_ajax_referer(...))` pattern every other nonce check in the codebase already uses.
- **[LOW] Migration retry-guard operated at coarser granularity than the work it was protecting.** `maybe_upgrade()`'s v1.1→v1.2 step ran three ALTER TABLE statements (add column, drop index, re-add index) behind a single guard checking only whether the column existed. A partial failure — column added successfully, index correction failed — would correctly prevent `update_option()` from advancing the stored version (that part already worked, from the v3.3.1 migration-failure fix), but on the *next* request, the guard would find the column already there and skip the entire block, including the index correction that never actually completed — silently leaving `unique_like` without `guest_token` in it, permanently, with no further retry. The column-existence check and the index-correctness check are now independent guards, so a failure in one doesn't mask the other from being retried.
- **Corrected two stale/inaccurate docblocks**: `class-rest-api.php`'s class-level comment claimed this class registers the Google OAuth callback route — it never has; that route is registered entirely independently in `class-oauth-google.php`. And the README's security table claimed `$wpdb->prepare()` is used "throughout" for SQL injection prevention — two `IN()` clauses use direct interpolation of `absint()`-cast ID arrays instead (safe, and a deliberate choice documented at the code level since v3.2.5, but not accurately described as `prepare()` specifically).
- **Removed 4 dead fields from the localized JS config**, discovered while verifying the OAuth docblock finding above: `googleAuth` (pointed to a REST route, `vibe-comments/v1/google-auth`, that was never registered anywhere — even reachable, this field was never read by any JS; the actual Google auth flow goes through the `ajax_google_auth()` admin-ajax action instead), `restUrl`, `loginUrl`, and `siteName` — all confirmed via full-codebase grep to have zero references anywhere in the JS or templates.

### Documentation
- **Added an operational note to the Google OAuth Setup section** about email-based account matching — standard "Sign in with X" behavior, not a plugin-specific design choice, but worth explicit awareness: a verified Google login matches to an existing WordPress account by email, so a visitor's Google account and a pre-existing WordPress account sharing an email will result in that visitor logging into the existing account's role and capabilities.

## [3.5.3] — 2026-07-03

### Fixed
- **Footer buttons overflowing/breaking on comments with all 4 possible actions** (reaction pill, Reply, View/Hide Replies, Pin/Unpin — only occurs on a pinned comment that also has replies). `.vibe-comment-footer` had no `flex-wrap`, defaulting to `nowrap`, which forced all 4 items onto one line; flex then shrank individual buttons to fit, and since none of them had `white-space: nowrap`, the squeezed button's own text wrapped internally (visibly, "Hide replies" broke into "Hide" / "replies" across two lines). Fixed with `flex-wrap: wrap` on the container plus `flex-shrink: 0` and `white-space: nowrap` on every footer item (reaction summary, Reply, View/Hide Replies, Pin/Unpin) — nothing gets squeezed anymore; the row wraps as whole buttons onto a second line instead when it doesn't fit.
- **Pinned badge rendering wider on the post author's own pinned comments than on other users' pinned comments**, despite identical badge markup and CSS. Root cause: `.vibe-comment-meta` is a `flex-direction: column` container with no explicit `align-items`, which defaults to `stretch` — every child (pinned badge, author-name line, timestamp) gets stretched to match the width of its *widest sibling*. On the post author's own comments, the "Author" badge sitting next to their name made that line wider than a regular commenter's plain name, and the pinned badge — a sibling in the same container — got stretched to match, even though "📌 Pinned" itself needs far less space. Regular commenters' pinned comments never showed this because their name line was never wide enough to stretch anything. Fixed with `align-items: flex-start`, which makes every child in this container size to its own content, independent of its siblings.

## [3.5.2] — 2026-07-03

**This is the confirmed fix for the v3.5.0 site-down crash.** v3.5.1 was defensive hardening shipped without the actual error text; this release was built directly from the real PHP parse error once the server's own log became available.

### Fixed
- **[CRITICAL] Parse error — `class-ajax-handler.php` line 579, "unexpected identifier 'vc_replies_', expecting function."** Two docblock comments contained the prose shorthand `vc_load_*/vc_replies_*`, intended as "the vc_load_ and vc_replies_ prefixed transients." The character sequence `*` immediately followed by `/` — completely coincidentally, from "vc_load_" ending in an implied wildcard and "/vc_replies_" starting the next path-like fragment — is PHP's literal comment-close token. The docblock terminated mid-sentence at that exact point, and everything after it (starting with `vc_replies_`) was parsed as actual PHP code sitting in the class body, which is exactly what produced "expecting function": PHP was at a point where only a new class member declaration is valid, and found a bare identifier instead.
  - This is a fundamentally different bug class than anything checked in v3.5.0's or v3.5.1's verification passes. Brace/paren balance checks are structurally blind to it — comment delimiters don't touch braces or parens at all, so a file can have perfectly matched `{}`/`()` counts while still containing this exact parse error. It also wasn't a typo'd method name, a duplicate declaration, or PHP-version-incompatible syntax — the three specific classes that were checked for. It was invisible to every verification method used because it's a category none of them were built to detect.
  - Both instances fixed (line 579 and an identical occurrence at line 600, in a different docblock, that had not yet triggered its own parse error only because PHP stops at the first failure it encounters — it would have broken again immediately after 579 was patched if only one had been fixed). Rephrased rather than just inserting a space, to remove the ambiguity entirely rather than narrowly avoid triggering it.
  - **Verification added going forward**: every file was re-scanned for the precise signature (`[a-zA-Z0-9_]\*/` — a word character directly adjacent to a comment-close token, the actual pattern that caused this) across every PHP, JS, and CSS file, plus a broader adjacent-character sweep. Zero remaining instances confirmed. The broader sweep did surface three matches in the JS file, all confirmed as false positives — legitimate regex literals (`[^&]*/g`, `\*([^*\n]+)\*/g`) where `*` is a quantifier/escaped-literal and `/` is the regex's own closing delimiter, not a comment boundary at all; PHP doesn't share this specific ambiguity since its regex patterns live inside string arguments rather than bare language syntax.

## [3.5.1] — 2026-07-02

Emergency hardening release — issued after a v3.5.0 site crash (WordPress "critical error" screen) with no confirmed root cause, due to `WP_DEBUG_LOG` being unavailable on the reporting environment. This release does not claim to have found and fixed a confirmed bug; it closes a real gap found during the investigation and provides a path to actual diagnosis.

### Fixed
- **`Vibe_Comments_Activator::maybe_upgrade()` and `Vibe_Comments_Schema::init()` were the only two subsystem-touching calls in `init()` not wrapped in the same `try/catch(Throwable)` pattern every other subsystem instantiation already used.** If either throws at runtime for any reason, it previously took down the entire site with an uncaught fatal instead of degrading gracefully like every other subsystem does. Both now match the existing pattern: caught, logged via `error_log()` unconditionally (visible in the server's native PHP error log regardless of whether `WP_DEBUG_LOG` is configured — see debug-logger.php's own reasoning for using `error_log()` specifically for this class of failure), and the rest of the site keeps functioning if either one fails.
- **`load_comments()`'s docblock still described the pre-v3.5.0 architecture** — claimed `Cache-Control: public, s-maxage=120` (edge/CDN-cacheable) and explicitly stated user-specific reaction state was excluded from the response. Both are now false: the cache is `private` (browser-only, for the reasons documented in v3.5.0's entry above) and `user_reaction` is included via `apply_user_reactions_overlay()`. Corrected to describe the actual current behavior.

### Diagnostic notes for anyone hitting this
An exhaustive static review of every file that loads unconditionally on every request (all of `class-ajax-handler.php`, `class-database.php`, `class-oauth-google.php`, plus `vibe-comments.php`, `class-activator.php`, `class-admin.php`, `class-schema.php`, `class-template-loader.php` — every line, cross-referencing every method call against actual definitions, checking for duplicate declarations, checking for PHP 8.0+/8.1+ syntax that would parse-fail on a PHP 7.4 host) found zero syntax errors. If a v3.5.0 site crash recurs after this release, the actual cause is almost certainly environment-specific (host PHP version/extensions, a pre-existing database state issue, a conflict with another plugin) rather than a plugin-code parse error, and the fastest path to a real answer is the host's own server-level PHP error log — on Hostinger specifically, `hPanel → Advanced → PHP Configuration → enable "logErrors"`, then check `/.logs/error_log_[yourdomain]` via File Manager. This is independent of `WP_DEBUG_LOG` in `wp-config.php` and works even when that path doesn't.

## [3.5.0] — 2026-07-02

Exhaustive audit pass — every PHP/JS/CSS file read fresh end-to-end, plus independent verification of a separately-submitted third-party audit (every claim checked against actual code; several accepted, two rejected after tracing didn't support the claimed mechanism, one of the third-party audit's own "Secure ✅" findings was itself incomplete).

### Fixed — Security
- **[HIGH] Guest and logged-in users' own reaction state was never shown on initial page load.** `format_comment_tree()`'s return array never included a `user_reaction` field at all — every comment always looked un-reacted-to on first render, for every visitor, regardless of whether they actually had an active reaction. Logged-in users only ever saw it self-correct because `initComments()` unconditionally calls `syncReactions()` for them; guests got no equivalent call on initial load and only self-corrected after the first 30-second polling tick (not "never," as initially reported, but a real gap for up to 30 seconds on every fresh page load). Root-caused and fixed once, at the source, so every caller benefits: `format_comment_tree()` now accepts a `$user_reactions_map` and includes `user_reaction` in its output; `load_comments()` and `load_replies()` both resolve the requester's identity (user_id or guest UUID, sent via a new `vibe_guest_id` query param on all four affected GET requests) and apply it via a new `apply_user_reactions_overlay()` helper.
  - **This fix required solving a second problem it exposed**: the comment-list cache (`vc_load_*`/`vc_replies_*` transients) has no user identity in its key — it's the same cached blob served to every visitor of a post/page. Baking `user_reaction` directly into what gets cached would have leaked one visitor's private reaction state to every other visitor served from that cache within the TTL window. Fixed by applying the overlay strictly *after* the anonymous version is already cached, on every response regardless of whether it came from a cache hit or a fresh query.
  - **This in turn required changing `set_public_cache_headers()`** from `Cache-Control: public, s-maxage=120` (explicitly CDN/shared-cache-cacheable, with LiteSpeed edge tagging) to `private, max-age=120` (browser-only). The response is now always personalized to the requester; the old headers would have let Cloudflare or LiteSpeed's edge tier cache one visitor's private reaction state and serve it to every other visitor of the same post for up to 2 minutes — a materially worse bug than the one being fixed. The underlying PHP-side transient cache (which avoids the DB query) is completely unaffected and still functions exactly as before; only the HTTP-level edge-cacheability changed.
- **[MEDIUM] `class-schema.php`: `comment_author` used raw in JSON-LD output while `comment_content` on the same file correctly had `wp_strip_all_tags()` applied.** Combined with `JSON_UNESCAPED_SLASHES` being enabled, a `</script>` sequence in an author name — from any source outside this plugin's own sanitized submission path (admin edit, import, a different plugin, legacy data) — could break out of the `<script type="application/ld+json">` block and inject arbitrary HTML into the page `<head>`. Fixed at the field level (`wp_strip_all_tags()` on `comment_author`, matching `comment_content`) and at the encoding level (`JSON_HEX_TAG | JSON_HEX_AMP` added to the `wp_json_encode()` call — still fully valid, spec-compliant JSON; a JSON-LD parser decodes the resulting `\u003C`/`\u003E` escapes identically to the unescaped characters).
- **[MEDIUM] `load_replies()` had no rate limiting at all** — every other AJAX action in this file does. Its cache is keyed per `comment_id`, unlike `load_comments()`'s page-scoped key, so an attacker enumerating many different comment IDs bypassed the cache benefit entirely with nothing bounding request volume. Added a 2-second per-IP-per-comment cooldown, matching the pattern used everywhere else in this file.
- **[LOW] `enable_google_login` setting silently re-enabled itself after being explicitly unchecked.** HTML checkboxes submit nothing when unchecked; `sanitize_settings()` only wrote the key to the stored option when it was present in `$_POST`, so unchecking and saving dropped the key entirely rather than storing `false`. The consumption logic then fell back to "enabled if `client_id` is set" — re-enabling Google login the admin had just explicitly turned off. Fixed by writing the boolean unconditionally (confirmed the settings page has exactly one `<form>` covering all fields together, so absence unambiguously means "unchecked," not "not part of this submission").
- **Missing `ABSPATH` guards added to 7 files** that had none: `class-activator.php`, `class-admin.php`, `class-ajax-handler.php`, `class-database.php`, `class-deactivator.php`, `class-rest-api.php`, `class-template-loader.php`. (`debug-logger.php`, `class-schema.php`, the main plugin file, and `uninstall.php` already had appropriate guards.)

### Fixed — Bugs
- **[HIGH] Comment UI completely hidden on any closed-comments post, even with existing comments.** `class-template-loader.php`'s `load_template()` bailed to the theme's default template whenever `!comments_open()`, with no check for existing comments — making `templates/comments.php`'s own carefully-written handling for exactly that case (its own top-of-file gate already correctly checked for existing comments) permanently unreachable. Combined with `class-schema.php` correctly outputting JSON-LD for closed-with-comments posts (a separate earlier fix), this meant Google could index a comment section a human visitor couldn't see through this plugin's own UI on the same post. Now uses `get_comments_number()` (the same primitive `templates/comments.php` itself already relies on a few lines into that file, safe-anywhere with no dependency on WP's comment query loop having run yet) to only redirect away from the plugin's template when there are truly zero comments AND commenting is closed.
- **[HIGH] Four separate, inconsistent implementations of "N Comments" heading text.** `templates/comments.php` (PHP) and `fetchCommentCount()` (JS) both correctly used the localized `config.oneCommentText`/`config.manyCommentsTemplate` strings. `initComments()` and `incrementCommentHeading()` each independently hardcoded English text (`'No Comments Yet'`, `'1 Comment'`, `total.toLocaleString() + ' Comments'`) that silently overwrote whatever had already been correctly localized, on every "Load Comments" click and every new comment submission. Consolidated into one shared `commentCountText()` function all four call sites now use. Also resolved a UX duplication in the process: `initComments()`'s "No Comments Yet" text was redundant with the empty-state block's own "Be the first to share your thoughts" message directly below it — the 0-comment case now consistently renders an empty (CSS-hidden) heading everywhere, matching what PHP and `fetchCommentCount()` already did.
- **[MEDIUM] `loadMoreComments()` ignored the currently active sort mode.** Newly fetched pages always arrive in the server's default (newest-first) order — `load_comments()` has no sort parameter — and were simply appended, landing at the bottom of an already-resorted (oldest or most-liked) list and breaking the visual order the user had chosen. Root-caused: the original sort implementation snapshotted "load order" once and reversed that fixed array for "oldest" mode — a snapshot that couldn't account for comments added later via Load More even if re-triggered. Rewritten so all three sort modes always read live DOM state (reusing the existing `restoreChronologicalOrder()` utility for "oldest," matching how "most liked" already worked) rather than depending on a stale snapshot; `loadMoreComments()` now re-applies the active sort after appending a new page.
- **`maybe_upgrade()` could silently mark a partially-failed database migration as complete**, permanently, with no further attempt to self-heal and no error visible anywhere. None of its `$wpdb->query()` (`ALTER TABLE`) calls checked their return value; if one step in the sequence failed, execution continued to the next step anyway, and `update_option('vibe_comments_db_version', ...)` still ran unconditionally at the end — meaning `maybe_upgrade()` would never run again for that site, permanently. Now checks every step's result, logs failures via `error_log()`, and only advances the stored version number when every step genuinely succeeded — a failed migration now correctly retries on the next request instead of being marked done.
- **`verify_jwt()`'s comment claimed "kid not found... bust cache and try once more"** but the code only busted the cache for the *next* login attempt and failed the *current* one — a user hitting a Google key-rotation window got a hard login failure requiring a manual retry. Now genuinely retries within the same request: a forced-fresh JWKS fetch and second kid lookup before giving up for real.
- **A fully dead caching subsystem removed**: `get_comments_for_post()`, `get_comments_cache_version()`, `increment_comments_cache_version()`, and `clear_post_comments_cache()` formed an object-cache-versioned comment-list cache with zero read-side callers anywhere in the codebase (confirmed via full-codebase grep) — the actual comment list is served entirely through `load_comments()`'s own, separate `vc_load_*` transient cache. The only thing this dead code was doing in production was one wasted `wp_cache_set()` call on every single comment submission.
- **Three orphaned docblocks removed** — leftover fragments from earlier str_replace edits this session, same failure class as an already-fixed JS syntax error from a prior release, just non-fatal this time: a stale "Load all nested comments... in one query" docblock sitting before `get_replies_map()`'s real (and functionally opposite) docblock in `class-database.php`; a stale "Fetch live comment count..." docblock sitting before `getGuestId()`'s unrelated real docblock in the JS file; and a duplicate pre-fix cache-headers docblock left behind by this session's own `set_public_cache_headers()` edit, sitting directly above the corrected one.
- **`class-rest-api.php`'s class-level and method-level docblocks said "WP_DEBUG mode"** for when debug endpoints activate; the actual gate has been `VIBE_COMMENTS_DEBUG_TOOLS` since a much earlier release. Anyone configuring a site from the documentation alone would have set the wrong constant and never gotten the debug endpoints to activate.

### Fixed — Accessibility
- **No `<noscript>` fallback anywhere** — this plugin's entire comment system (list, form, reactions) is AJAX-driven with no server-rendered content in the template at all; a JavaScript-disabled visitor saw a "Load Comments" button that did nothing, with zero explanation. Added an honest `<noscript>` notice (with the existing comment count, properly pluralized via `_n()`) rather than attempting a parallel non-JS posting system.
- **New-comments polling banner had no `aria-live`/`role="status"`** — a screen reader user got no notification at all that new comments had arrived; the banner was a purely visual DOM insertion.
- **No focus management after successful comment submission** — focus stayed on the now-cleared, now-empty textarea, giving a keyboard/screen-reader user no confirmation their comment actually landed or where. Focus now moves to the newly posted comment (`tabindex="-1"`, removed again on blur so it doesn't linger as a permanent tab stop).
- **Character-limit textarea had no `aria-describedby`** linking it to the counter — the counter `<div>` didn't even have an `id` to link to. Added both.
- **No `prefers-reduced-motion` support anywhere.** Added a single universal rule (`animation-duration`/`transition-duration`/`scroll-behavior` forced to instant) that covers every current animation in this file and — per the CSSOM View spec, which browsers honor — also covers every `scrollIntoView({behavior:'smooth'})` call in the JS, with no JavaScript changes needed.
- **Inline styles (`style.cssText`, `style.marginTop`) in `showError()`, `showSuccess()`, and `moveFormToComment()`** would silently break under a Content-Security-Policy that disallows `unsafe-inline` styles. Moved to ordinary CSS classes (`.vibe-message-error`, `.vibe-message-success`, `.vibe-reply-container`) — same exact visual values, just no longer inline.

### Changed
- **`escapeHtml()` no longer creates a DOM element on every call** — replaced with a direct, verified-equivalent regex chain (same four characters, same mandatory `&`-first ordering to avoid double-escaping), made explicitly defensive against non-string input to preserve the same implicit robustness the DOM-based version had via `textContent`'s coercion.
- **A `debug` flag is now exposed to JS** via the localized config (mirrors `VIBE_COMMENTS_DEBUG_TOOLS` server-side) — `fetchCommentCount()`'s previously fully-silent failure path now `console.warn`s when a developer has deliberately enabled debug tools, without ever producing console noise for a real visitor by default.

### Considered and explicitly rejected
- **Gating `maybe_upgrade()` to admin-only requests** (a third-party audit suggestion, initially seemed reasonable) — traced through the actual consequences and reversed course: `maybe_upgrade()` is the sole mechanism for in-place upgrades on an already-active install (`activate()`'s `dbDelta()` doesn't re-run on a same-slug file replace). Gating it to `is_admin()` would mean front-end requests keep running the *new* plugin code against an *old*, un-migrated schema until an admin happens to next visit wp-admin — real breakage risk for a performance "fix" that was close to zero benefit anyway, since the option involved is autoloaded and already loaded into memory by WordPress's own `alloptions` cache on every request regardless of this plugin's existence.
- **Two third-party audit findings rejected after the claimed mechanism didn't survive tracing**: a claim that sorting would undo active search filtering (the DOM reorder operation used never touches `style.display`, so there's no path by which a hidden comment becomes visible again) and a claim that `count_descendants()` had exponential worst-case behavior on linear reply chains (comment parent/child relationships form a proper tree — different top-level comments' subtrees never overlap, and the cited "linear chain" example has exactly one top-level comment, visited exactly once).
- **Renaming `toggle_like`/related identifiers for naming-purity reasons** (third-party suggestion) — real breakage risk for any external reference to the current action name, zero functional benefit. Not implemented.

## [3.4.0] — 2026-06-30

### Added
- **Decoupled comment-count heading** — the "N Comments" heading now self-corrects to the live count on every page load via a new `get_comment_count()` endpoint, without requiring a full-page cache purge on every comment event. Previously, `sync_and_purge()` called `purge_page_cache()` (a full LiteSpeed/Cloudflare page eviction) on every single comment purely to keep this one number fresh — evicting the entire cached page (images, hero content, everything) for one integer, and *still* not delivering instant freshness, since the purge only evicts, it doesn't regenerate; the next visitor after the purge paid the full cold-render cost. `sync_and_purge()` no longer calls `purge_page_cache()`. The new endpoint reads `vibe_comment_count_{id}` (already kept synchronously correct) behind a 20-second transient, so concurrent requests across many simultaneous visitors collapse into one DB read per TTL window rather than one per visitor. `purge_page_cache()` itself is untouched and still available for manual/future use — it drives W3 Total Cache, WP Super Cache, and Comet Cache compatibility beyond just the count, so the function was kept intact rather than deleted; only its automatic call from the comment-event path was removed.
- **Newest-first comment order (was oldest-first)** — `load_comments()`'s default `order` changed from `ASC` to `DESC`. The sort toggle (`initSortToggle()`) was restructured so its "restore original order" behavior now correctly means "newest" (matching the new server default) instead of "oldest" — clicking through modes still cycles Newest → Oldest → Most Liked, but the underlying snapshot/restore logic is the mirror image of pre-3.4.0 since the load order itself flipped. The template's initial sort button state (title, `data-mode`, arrow icon) was updated to match.
- **Collapsed replies with on-demand loading, Instagram/Reddit-style** — top-level comments no longer arrive with their full reply tree embedded. `load_comments()` now returns each top-level comment with a `reply_count` integer instead of nested `children`; a "View N replies" button renders when `reply_count > 0`. Clicking it fires a new `vibe_load_replies` endpoint that fetches and renders that thread's ENTIRE nested subtree (all levels) in one request — one click reveals the whole conversation, not one click per nesting level. A second click hides the thread again without re-fetching (existence of the already-built `<ul class="children">` is the state signal). New database layer: `get_replies_map($post_id, $root_ids, $max_levels)` fetches descendants level-by-level via `IN()`, scoped to only the requested root IDs — replacing `get_children_map()`, which unconditionally fetched every approved reply for the *entire post* on every single `load_comments()` call regardless of how many threads were on the current page or how many were ever expanded. `get_children_map()` had zero remaining callers after this change and was removed.
  - **Cache-scoped invalidation**: a new reply purges only its specific parent's cached subtree (`vc_replies_{parent_id}`, 120s TTL) via a shared `purge_reply_cache_if_needed()` helper, called from `submit_comment()` and all three comment-status hooks (`on_comment_approved`, `on_comment_deleted`, `on_comment_status_set`). No enumeration needed — the affected parent is always already known at each call site.
  - **Reply submission UX**: posting a reply auto-reveals it immediately, handling all three possible parent states — no `View Replies` button existed yet (first reply on this comment: create the container, show it directly, no button needed since there's nothing to collapse), thread was collapsed (auto-expand and reveal), or thread was already expanded (append directly, no visible change in state). The user's own reply is never the one thing that silently disappears behind a stale button.
  - **Top-level insertion now prepends, not appends**: a brand-new top-level comment (via direct submission or the live-polling "N new comments" banner) is inserted at the *top* of the list, matching the new newest-first order. Under the old ASC-default + append-at-bottom pairing, this was correct; under the new DESC default it would have placed a fresh comment visually among the oldest ones on the page.

### Known limitation (not addressed in this release)
- **Live polling does not surface new replies to already-expanded threads.** This is a pre-existing limitation, not something introduced by this release: `load_comments()`'s polling branch has always queried with `parent = 0` unconditionally (true before v3.4.0 too), so it only ever detects new *top-level* comments. A new reply to a thread you already have open won't appear until you reload the page or collapse/re-expand that thread. Fixing this properly means teaching the polling fast-check to distinguish "new top-level activity" from "new reply activity" and surfacing a per-thread indicator — a meaningfully separate feature from what was requested here, not bundled into this release to avoid further scope creep on an already large change.

## [3.3.2] — 2026-06-30

### Fixed
- **[HIGH] Reaction counts reverted on refresh within the 120-second cache window** — `toggle_reaction()`'s `invalidate_reaction_cache()` only ever cleared two `wp_cache_*` object-cache entries (`reactions_{id}` and `user_reaction_{id}_...`). It never touched the `vc_load_{post_id}_{page}_{per_page}` transient that `load_comments()` uses to cache its *entire* response — comment list and reaction counts together — for 120 seconds. Sequence that produced the bug: comments load and get cached → user reacts → DB write succeeds and the toggle response correctly shows the new count (read fresh from the DB, not from the stale cache) → user refreshes and reloads comments within that 120-second window → `load_comments()` serves the still-valid cached snapshot from *before* the reaction, making it look like the click never saved. Waiting past 120 seconds before refreshing always showed the correct count, which was the tell.
  - **Fix:** `toggle_like()` now calls `purge_comments_data_cache($post_id)` — the same function `sync_and_purge()` already uses for comment post/delete/status-change events — immediately after a successful reaction write, using `$comment_obj->comment_post_ID` (already fetched earlier in the handler for validation, so this costs zero extra queries).
  - **Performance note:** `purge_comments_data_cache()` does up to 15 `delete_transient()` calls (3 `per_page` values × 5 pages) per invocation. This is the same cost the codebase already accepts on every comment submission via `submit_comment()` → `sync_and_purge()`, so it's an existing, accepted tradeoff being extended to a second trigger — not a new category of cost. It is bounded per-actor by the existing 5-second reaction rate limit. If reaction volume on high-traffic posts ever makes this measurable (plausible, since reacting is lower-friction than commenting and could outpace comment volume on viral content), the cheaper fix is a cache-key versioning scheme — bump a single per-post version transient instead of deleting up to 15 keys — mirroring the `get_comments_cache_version()` pattern already used elsewhere in `class-database.php` for a different cache. Not implemented now: it would require changing the `vc_load_*` key construction in `load_comments()` and touching the currently-working `purge_comments_data_cache()` path, which is more surface area than this fix needed.
- **Comment count heading ("N Comments") was never affected by this bug** — it reads from `vibe_comment_count_{post_id}` in `wp_options`, which `sync_and_purge()` updates correctly and independently of the reaction cache gap above.

## [3.3.1] — 2026-06-29

This release combines findings from an internal exhaustive audit with a third-party audit document. Every external finding was independently re-verified against the actual codebase before being applied — several were stale (already fixed earlier this session), one mischaracterized how the migration code actually works, and one recommendation was deliberately rejected. Details below.

### Fixed — Security
- **debug-logger.php: filesystem operations now wrapped in try/catch** — `wp_mkdir_p()` and the directory check ran with no exception handling. A read-only filesystem or permissions error during a debug-enabled session could throw uncaught, crashing the request. The logger must never be the reason a page fails to load.
- **Guest token UUID validation tightened to strict canonical format** — Previously, malformed input was cleaned via `preg_replace()` (stripping non-hex/hyphen characters) and anything left in the 32–40 char range was accepted. Two different malformed inputs containing different disallowed characters could strip down to an identical cleaned string and collide on the same guest token. Now requires an exact match against `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i` — the only format our own `getGuestId()` JS ever produces. Anything else falls through cleanly to the existing IP-based fallback.
- **`ajax_google_auth()` nonce check missing third parameter** — Used `check_ajax_referer('wp_rest', 'nonce')` without `false` as the third argument, so a nonce failure called `wp_die()` (a blank/broken page) instead of returning a JSON error the UI could handle gracefully. Now consistent with every other AJAX handler in the plugin.
- **`sync_likes` had no rate limit** — Every other write endpoint has a cooldown; this one didn't, allowing unlimited 100-ID batch requests (2 DB queries each) from any client holding a valid nonce. Added a 3-second per-IP cooldown.

### Fixed — Bugs
- **`maybe_upgrade()` migration order** — already fixed in v3.3.0, included here for completeness of the audit trail.
- **`load_comments()` declared `global $wpdb` twice** in different branches of the same method. Consolidated to a single declaration at the top of the method.
- **Redundant `Vibe_Comments_Database` instantiation** in the polling+reaction-counts branch of `load_comments()` — `$db` was already in scope from earlier in the same method.
- **`loadMoreComments()` scroll jitter** — `scrollIntoView()` fired once per comment in a batch (e.g. 10 competing smooth-scroll animations for a 10-comment batch). Now scrolls once, to the first newly-appended comment, after the whole batch has rendered.
- **Three bare `fetch()` calls with no timeout** (`refreshNonce()`, `initGoogleAuth()`, `initPinComment()`) — every other network call in the file uses `fetchWithTimeout()`. A hung request on these three previously gave zero user feedback: nonce silently goes stale, Google login button does nothing, pin button hangs forever. All three now use `fetchWithTimeout()` with appropriate timeouts and properly re-enable their trigger buttons in both the success and failure paths.
- **Comment search matched the entire `<li>` textContent**, including "Reply", "Pin", reaction labels, and timestamps — so searching "Reply" matched every single comment. Now scoped to `.vibe-comment-content` and `.vibe-comment-author` only.
- **`initCommentsTrigger()` used a manual `loaded` boolean flag** that left a dead click listener checking the flag on every subsequent click forever. Replaced with `{ once: true }`, which auto-detaches the listener after first use.
- **Dead `wpautop()` function removed** — zero call sites anywhere in the file (it sat inside an IIFE that exposes nothing externally, so nothing outside the file could call it either).
- **Two pairs of orphaned/stale docblocks removed** from `vibe-comments.js` — a leftover "Google OAuth initiation" comment sitting above `initCommentsTrigger()`, and a leftover "AJAX comment submission" comment sitting above `initDraftSave()`.

### Fixed — Internationalization
- **All 22 hardcoded English strings in `wp_send_json_error()` calls** (`class-ajax-handler.php`) wrapped in `__('...', 'vibe-comments')`. These are displayed directly to end users via the JS `showError()` function and were not translatable.
- **All 10 hardcoded English strings passed to `oauth_error()`** (`class-oauth-google.php`) wrapped in `__()`. These are shown to users after a failed Google sign-in attempt.
- **`load_plugin_textdomain()` was never called** — the plugin header declares `Text Domain: vibe-comments`, but without this call `__()`/`_e()` always fall back to the English source string even with valid `.mo` translation files present. Added on `init`, loading from `/languages`.

### Fixed — Coding Standards / Housekeeping
- **`REACTION_DEFS` changed `var` → `const`** (already in v3.3.0) plus a broader pass: every function-scoped `var` in `initSortToggle()`, `initSearch()`, and `initDraftSave()` that is never reassigned is now `const`; variables that genuinely are reassigned (`idx`, `originalOrder`, `timer`, `count`, `saveTimer`) remain `let`.
- **12 `vibe_log()` calls at class-method scope were ungated and ran on every single page load** even though `vibe_log()` itself no-ops without the debug flag — the function-call overhead existed regardless. All success-path logs are now gated behind `VIBE_COMMENTS_DEBUG_TOOLS`. Error-path logs in `catch` blocks now ALSO call PHP's native `error_log()` unconditionally — previously a fatal subsystem failure (REST API broken, OAuth broken, or the entire plugin failing to instantiate) produced zero record anywhere unless debug tools happened to be on. Silent total failure was a worse problem than log noise.
- **CSS: three duplicate selector blocks removed** — `.vibe-new-banner`, `.vibe-comment-content.vibe-content-collapsed`, `.vibe-read-more`, and `.vibe-comment-content a[rel~="ugc"]` were each defined twice with identical declarations. First (dead/unreachable) occurrence of each removed.
- **CSS: dead `.vibe-comments-nav` rules removed** (5 selector blocks) — the plugin uses AJAX Load More exclusively; no `<nav>` pagination element exists anywhere in the templates or JS.
- **CSS: `--vibe-bg-alt` custom property now declared in `:root`** — it was referenced via `var(--vibe-bg-alt, #f3f4f6)` in 3+ places but never actually defined, so a theme attempting to override it via CSS custom properties had nothing to target.
- **CSS: keyboard focus indicators added** — `.vibe-sort-icon-btn`, `.vibe-search-input`, `.vibe-reaction-summary`, `.vibe-reaction-option`, and `.vibe-pin-btn` all set `outline: none` (or inherited no focus style) with no replacement, leaving keyboard-only users with zero visual indicator of which control was focused (WCAG 2.1 SC 2.4.7). Added `:focus-visible` outline rings to all five — `:focus-visible` only fires for keyboard navigation, so mouse users see no visual change.
- **CSS: `.vibe-btn-load-comments` now styled** — applied in the template but never defined in the stylesheet, leaving the page's primary engagement CTA with only the generic unstyled `.vibe-btn` base (no background color). Now styled to match `.vibe-btn-primary`.
- **Stale comment explaining a code deletion removed** from `class-ajax-handler.php` — a comment describing why `get_comment_count` was removed has no value going forward; that history belongs in this changelog, not in source.

### Verified, not changed
- **`'use strict'`** — already present at the top of the JS IIFE. A third-party audit flagged this as missing; it is not.
- **OAuth cookie subdirectory path** — already fixed in this session prior to the third-party audit being read; the audit's finding described pre-fix code.
- **Transient timeout cleanup** — `maybe_upgrade()` already deletes both `_transient_vc_%` and `_transient_timeout_vc_%` in a single query; a third-party audit's claim that timeout rows were orphaned does not match the actual code.
- **`dbDelta()` index-recreation risk** — `dbDelta()` is called exactly once, in `activate()`, only for the initial `CREATE TABLE` on a table that does not yet exist (so there is no data to lose). All schema migrations for existing installs run through `maybe_upgrade()`'s explicit, manual `ALTER TABLE` statements — not `dbDelta()`. The general WordPress-core quirk this finding describes is real, but does not apply to how this plugin's migration path is actually structured.
- **`add_cache_headers()` / `rest_api_init` timing vs. `set_public_cache_headers()`** — these two functions cannot conflict: `load_comments()` (which calls `set_public_cache_headers()`) is registered exclusively via `wp_ajax_vibe_load_comments` / `wp_ajax_nopriv_vibe_load_comments` (`admin-ajax.php`), which never triggers the `rest_api_init` hook or sets `REST_REQUEST`. `add_cache_headers()` only ever applies to genuine `/wp-json/vibe-comments/...` routes (the OAuth callback and the two debug/test REST endpoints). The two code paths are mutually exclusive by WordPress's own request routing and cannot both fire on the same request.
- **`wp_kses_post()` on `format_comment_tree()` output — deliberately not added.** `comment_content` is sent raw in the JSON response and is already correctly escaped client-side via `escapeHtml()` before any `innerHTML` insertion (verified). Adding server-side `wp_kses_post()` would run user content through a second, differently-scoped sanitization model (an HTML-tag whitelist intended for direct HTML output) before the client's own plain-text-escape-then-markdown pipeline runs — risking silently altered or mangled user-submitted text for no actual security gain, since the existing single point of escaping at the unsafe sink (`innerHTML`) is already correct and sufficient.
- **`@since` docblock tags, `declare(strict_types=1)`, new extensibility filters, PHPUnit tests** — all genuine, defensible suggestions, but out of scope for a bug-fix audit pass. `@since` tagging is high-effort, low-value busywork for code that isn't distributed via the WordPress.org repository (no tooling here parses it). `strict_types` is a behavior-changing flag with real regression risk across 10 files with no existing test coverage, and is not something to apply mechanically. These are noted for a dedicated future session if wanted, not bundled into this fix pass.

### Security

## [3.2.4] — 2026-06-24

### Security — Critical (from external audit)
- **[C1] `jwk_to_pem()` DER off-by-one fixed** — The outer SEQUENCE length in the SubjectPublicKeyInfo structure was computed incorrectly: `strlen(rsa_oid) + 1 + der_length_size(len) + len` miscounts by 1 because the leading `\x00` byte of the BIT STRING is part of the inner content but was excluded from the inner length calculation. Fix: build the complete BIT STRING object first (`$bitstring_content = "\x00" . $rsa_key_der; $bitstring = "\x03" . der_length(strlen($bitstring_content)) . $bitstring_content`), then compute the outer SEQUENCE length from its actual byte size. Also removes the now-unused `der_length_size()` helper method.
- **[C2] Login-CSRF via anonymous OAuth state** — `wp_create_nonce()` for anonymous users (uid=0, no session token) produces identical values within each ~12-hour WP tick. Any anonymous user who initiates a Google login gets the same state token as every other anonymous user in that window — a CSRF attacker can re-use anyone's state to complete their own login flow. Fix: `wp_generate_password(32, false, false)` generates a cryptographically random 32-char state token. The token is stored in a transient keyed by its MD5 hash AND simultaneously set as an HttpOnly SameSite=Lax browser cookie. The callback verifies BOTH (`hash_equals()` on cookie vs URL state). An attacker who intercepts a state token from a different browser cannot replay it — the cookie won't be present in their request.

- **[C4] Hardcoded approval status ignored Discussion Settings** — `$approved = 1` for logged-in users and `$approved = 0` for guests, regardless of site configuration. `wp_new_comment()` now determines the approval status via `wp_allow_comment()` which respects the Discussion Settings panel.

## [3.2.3] — 2026-06-23

### Security — Critical
- **Google JWT signature now fully verified (RS256)** — `class-oauth-google.php` completely rewritten. The original `decode_jwt_payload()` only base64-decoded the JWT payload and checked the `aud` claim — it never verified the RS256 signature. An attacker who knew your public Google Client ID (it's embedded in the JS config, so always visible) could forge a JWT, set any email in the payload, and the plugin would accept it — creating a WordPress session for any account including admins. Fix: `verify_jwt()` fetches Google's JWKS from `googleapis.com/oauth2/v3/certs`, caches the keys for 1 hour, matches the token's `kid` to the correct key, and calls `openssl_verify()` against the RS256 signature. No match = null return = authentication rejected. `jwk_to_pem()` converts Google's JWK format to PEM in-process — no external library needed.
- **`email_verified === true` now enforced** — Google can return accounts with unverified email addresses (e.g. federated identity providers). These are now rejected before any user lookup or creation.
- **Dead REST endpoints removed** — `class-rest-api.php` registered 6 endpoints (`/like`, `/likes/{id}`, `/comment`, `/comments/{id}`, `/likes-batch`, `/test`) that the frontend stopped calling in v2.0.0 when operations moved to admin-ajax. These endpoints still called DB methods (`toggle_like`, `user_has_liked`, `get_like_count`, `get_like_counts_batch`, `get_user_liked_batch`) that were deleted in v3.0.0 when the reactions system was introduced. Any direct HTTP request to those endpoints would have caused a PHP fatal error. All 6 removed. Only the debug endpoint (admin + WP_DEBUG only) and REST-based OAuth callback remain.
- **REST rate limiters used worker-local cache** — `class-rest-api.php` `check_rate_limit()` used `wp_cache_get/set` which is per-process. On a multi-worker PHP-FPM server (any VPS), attackers could bypass rate limits by distributing requests across workers. Moot now that the endpoints are removed, but the REST class is clean.
- **`uniqid()` replaced with `wp_generate_password(8, false)` for OAuth usernames** — `uniqid()` generates time-based values with limited entropy. `wp_generate_password(8, false)` is cryptographically random alphanumeric — 36^8 ≈ 2.8 trillion possibilities.

### Fixed
- **Comment count stale on trash/spam/delete** — `on_comment_approved()` only fired on `transition_comment_status` (approval direction). Trashing, spamming, or permanently deleting an approved comment left the `wp_options` count and all cache layers stale until the next approval event. Added `on_comment_deleted()` (hooks `delete_comment`) and `on_comment_status_set()` (hooks `wp_set_comment_status`) — both funnel through the new `sync_and_purge()` method which recalculates from DB, writes to `wp_options`, and busts all cache layers.
- **`anonymous@example.com` Gravatar collision** — all guest comments with no email address resolved to the same Gravatar (the identicon for `anonymous@example.com`). Every guest comment now gets a unique deterministic avatar via `md5('vibe_guest_' . $comment_id)@comments.local`. Different comment = different identicon = no collision.

### Added
- **`sync_and_purge()` private method** — single source of truth for count persistence and cache invalidation. All three comment status hooks call this instead of duplicating logic. Writes live count to `wp_options` before purging edge caches so cache rebuilds always read the fresh value.
- **`README.md`** — replaces `readme.txt`. Full documentation: feature list, caching architecture table, Cloudflare setup, security scorecard, DB schema, Google OAuth setup. Renders properly on GitHub.

### Removed
- **`readme.txt`** — replaced by `README.md`.

- Count query used `'number' => ''`; corrected to `'number' => 0`.

### Security
- Debug REST endpoint restricted to admin (`manage_options`).
- Rate limit added to AJAX comment submission.
- Nonce check added to AJAX comment submission.

## [1.2.0] — 2026-06-09

> First working release. Fatal error on comment submission resolved by
> bypassing the REST API entirely and routing through admin-ajax.php.
> Identified root cause: a conflicting plugin hooked into `comment_post`
> and threw a fatal error on every comment insertion site-wide.

### Added
- `class-ajax-handler.php` — new file. Handles comment submission via `wp_ajax_vibe_submit_comment` and `wp_ajax_nopriv_vibe_submit_comment`, bypassing the REST API hook conflict entirely.
- Guest identity persistence via `localStorage` (`vibe_guest_name`, `vibe_guest_email`).
- Gravatar fallback for guest comments with no email — uses `anonymous@example.com` instead of empty string.
- `ajaxUrl` in `wp_localize_script`.

### Fixed
- Fatal error on comment submission — REST API `/comment` endpoint triggered `comment_post` action which a conflicting plugin crashed. Submission now uses `admin-ajax.php` with direct `$wpdb->insert()`, bypassing all problematic hooks.
- Like/unlike toggle — `toggle_like()` always performed `DELETE + INSERT IGNORE` regardless of current state, making it impossible to unlike. Fixed to check existing state first and perform the correct operation.

### Changed
- Comment submission endpoint changed from `POST /wp-json/vibe-comments/v1/comment` to `POST /wp-admin/admin-ajax.php?action=vibe_submit_comment`.
